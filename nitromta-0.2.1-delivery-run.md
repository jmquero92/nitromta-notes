# NitroMTA 0.2.1 Local Delivery Run Report

- **Installation method and exact version:** Downloaded the official Linux x86_64 release archive (`https://github.com/nitrosend/nitromta/releases/download/v0.2.1/nitromta-0.2.1-x86_64-linux.tar.gz`), extracted `nitromta-0.2.1-x86_64-linux/nitromta`, and verified the binary version output: `nitromta 0.2.1` (`./nitromta --version`).
- **OS and architecture:** Ubuntu 24.04.4 LTS (Noble Numbat), kernel `Linux 7.0.0-31-generic x86_64` (`uname -srm`).
- **Exact commands run:**
  - Created an isolated working directory and initialized capture configuration on unprivileged ports:
    ```sh
    mkdir -p /tmp/nitromta_run/work && cd /tmp/nitromta_run/work
    /tmp/nitromta_run/nitromta setup --config config.toml --capture
    ```
  - Generated a 2048-bit RSA DKIM private key:
    ```sh
    openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out dkim.pem
    ```
  - Started the engine as an unprivileged user (`jmquero`):
    ```sh
    /tmp/nitromta_run/nitromta run --config config.toml
    ```
  - Provisioned account `1`, domain identity `example.test` with selector `s1` and the PEM private key, and SMTP login `app` over `./admin.sock`:
    ```sh
    key=$(jq -Rs . dkim.pem)
    /tmp/nitromta_run/nitromta admin --config config.toml <<END
    {"op":"put_account","account":1}
    {"op":"put_identity","account":1,"name":"example.test","selector":"s1","private_key":$key}
    {"op":"create_login","account":1,"user":"app"}
    END
    ```
    Output lines returned by `nitromta admin`:
    `{"ok":{"revision":1}}`, `{"ok":{"revision":2}}`, and `{"ok":{"revision":3,"user":"app","password":"<redacted-64-hex>"}}`.
  - Submitted one message over SMTP (`127.0.0.1:2587`) using `STARTTLS` validated against `./tls.crt`, authenticating as user `app`, with `From: app@example.test`, `To: proof@nitromta.com`, and `Reply-To` set to our inbox.
  - Checked queue and delivery status via `nitromta queue --config config.toml --json` and `nitromta explain --config config.toml --message c6c150d3200000`:
    ```text
    delivery 00c6c150d3400001 of message 00c6c150d3200000 to proof@nitromta.com
      state      finished, delivered, at 2026-11-05T18:07:45.232Z
      expires    2026-11-08T18:07:43.258Z
      attempts   1, 0 of them uncertain
    ```
- **Every change made to `config.toml`:**
  - Under `[delivery]`, uncommented `# port = 25` and changed it to `port = 2525` so outbound SMTP connects to `mta-proof.nitrosend.com:2525`.
  - Deleted the trailing `[capture]` section (`[capture]` and `directory = "./capture"`) at the bottom of `config.toml` so accepted messages are delivered over the network instead of written to `./capture`.
  - Kept `[store]` (`path = "./store.db"`, `keys = "./keys"`), `[submission]` (`listen = "127.0.0.1:2587"`, `hostname = "localhost"`, `certificate = "./tls.crt"`, `key = "./tls.key"`), `[ses]` (`listen = "127.0.0.1:4443"`), `[admin]` (`socket = "./admin.sock"`), and `[operator]` (`listen = "127.0.0.1:9090"`) at the unprivileged defaults generated by `setup --capture`.
- **Minutes from install to receipt:** Approximately 2 minutes from downloading and extracting `nitromta-0.2.1-x86_64-linux.tar.gz` (`18:06:00 UTC`) to receiving the `250 2.0.0` remote delivery receipt at `2026-11-05T18:07:44.830Z`.
- **Step that slowed us most:** Retrieving the 16-hex-digit message ID (`00c6c150d3200000`) after sending via Python `smtplib.SMTP.send_message()`, because `send_message()` returns `{}` (discarding the `250 2.0.0 <id>` post-`DATA` text), and once the delivery completed in ~1.5 seconds (`stored.in_flight` went from `1` to `0`), neither `nitromta queue` nor `nitromta list` exposes finished message IDs, requiring us to read `SELECT id FROM messages` from `store.db` (`55944598272344064` -> `0xc6c150d3200000`) to pass to `nitromta explain`.
- **Defect / documentation gap and exact reproduction:**
  - **Issue 1 (`explain` omits the final `250` remote reply on delivered mail despite `docs/operations.md`):** `docs/operations.md` (*"Why is this message waiting?"*) states that `nitromta explain --config config.toml --message <id>` shows *"for each of the message's deliveries: its state and since when, when it expires, how many attempts it has had and how many of them were uncertain, the egress it goes out from, the last reply its receiver gave with the receiver rules that reply matched"*. However, in `crates/engine-api/src/inspect.rs`, `last_reply` only populates when an attempt ends *without* delivering the message (`/// What the receiver said when its last attempt ended without delivering it`), even though the `250 2.0.0 receipt ...` remote reply is persisted in the SQLite `journal` table (position 2).
  - **Issue 2 (`explain --json` on nonexistent hex IDs vs decimal IDs):** Passing a nonexistent valid hex ID such as `1` or `999999` in `--json` mode returns exit code `0` with `{"ok":{"deliveries":[]}}` rather than a not-found error, whereas plain-text mode prints `no such message or delivery`. Conversely, passing the integer primary key from SQLite `messages.id` (`55944598272344064`) fails with `nitromta: malformed: message is an ID in hex` because `u64::from_str_radix(text, 16)` overflows `u64` on 17 digits.
  - **Exact reproduction:**
    ```sh
    # With nitromta 0.2.1 running after delivering message 00c6c150d3200000:
    /tmp/nitromta_run/nitromta explain --config config.toml --message c6c150d3200000 --json
    # Output omits last_reply even though journal row 2 contains "2.0.0 receipt https://runx.ai/r/...":
    # {"ok":{"deliveries":[{"at":"2026-11-05T18:07:45.232Z","attempts":1,"completion":"delivered","delivery":"00c6c150d3400001","expires":"2026-11-08T18:07:43.258Z","message":"00c6c150d3200000","recipient":"proof@nitromta.com","state":"finished","uncertain_attempts":0}]}}

    # Nonexistent hex ID in plain text vs --json:
    /tmp/nitromta_run/nitromta explain --config config.toml --message 999999
    # -> prints "no such message or delivery" (exit 0)
    /tmp/nitromta_run/nitromta explain --config config.toml --message 999999 --json
    # -> prints {"ok":{"deliveries":[]}} (exit 0, indistinguishable from an empty list)
    ```
- **One change we would make:** Include `last_reply` (the remote `250` acceptance response text from the journal/delivery record) in `nitromta explain` output for `finished, delivered` deliveries—and add a `nitromta list --config config.toml messages [--most <n>]` (or `--recent` flag on `queue`) so operators can look up recent message hex IDs and remote `250` queue/receipt identifiers directly from the CLI without inspecting `store.db` when an SMTP client library discards the post-`DATA` reply text.
